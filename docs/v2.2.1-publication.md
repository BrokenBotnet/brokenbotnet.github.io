## 📸 Deployment captures

Run these on the actual Compose host after the intended service has been upgraded. Replace `<service>` with its existing Compose service name. These commands inspect state and do not perform the upgrade.

### Tor version and valid configuration

```sh
clear
docker compose exec <service> sh -c 'tor --version; config validate'
```

Save as `version-config-validation.png`. The output must show the actual Tor version and successful validation. Configuration validity alone does not establish reachability.

### Source provenance

```sh
clear
docker compose exec <service> cat /usr/share/tor/source.json
```

Save as `source-provenance.png`. This file contains public source version, checksum and signer information. It is separate from proof that the process has restarted with the new image.

### Current-run health without identity fields

The pipe below uses host Python 3. It selects only the documented health fields; do not publish a raw bridge identity or a full container inspection.

```sh
clear
docker compose exec -T <service> doctor --json | python3 -c 'import json,sys; r=json.load(sys.stdin); h=r["health"]; names=("build_version","tor_version","relay_mode","liveness","readiness","config_valid","fresh","bootstrap","reason","reachable","errors"); print(json.dumps({"health":{k:h[k] for k in names if k in h}},indent=2))'
```

Save as `relay-diagnostics.png`. Keep the JSON types intact. Explain that local readiness and Tor's self-test are separate from external reachability and consensus membership.

Compare fingerprints privately before and after upgrade. Keep private keys, bridge addresses/credentials, deployment ENV, recovery identities and full inspect output out of screenshots. If showing encrypted archive verification, use a newly created and verified recovery set and publish only its result, not key material or plaintext archive contents.
